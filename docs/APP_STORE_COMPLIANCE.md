# App Store compliance (Phase 0 research)

Date: 2026-11-13. Author: WP-R. This is a technical reading of public documents, not legal advice and not a prediction of App Review outcomes. Nothing was submitted or built.

Marking: **V-doc** = stated by the linked primary source. **U** = inference or unconfirmed. "Verification status" in the table is always limited to: policy/API text read (V-doc) and implementation not built. No row is verified on a device or in review.

Sources: [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) (page text fetched 2026-11-13; the page does not print its own revision date; Apple's news feed lists the latest update as 2026-10-16, V-doc [Apple news](https://developer.apple.com/news/?id=guidelines)). Only about the first 100,000 of 114,428 characters of the guidelines page were read (truncated after 5.2), so sections beyond 5.2 were not read (U for anything there, e.g. section 1 content rules, 3.x payments).

## 1. Which guidelines apply to Krypa

Krypa's App Store identity must be **a web browser**, not an app catalog. The decisions below follow from that.

| Guideline | Text (paraphrase, quote under 15 words) | Applies as browser | Applies as app catalog | Note |
|---|---|---|---|---|
| 2.5.1 | "Apps may only use public APIs and must run on the currently shipping OS." | Yes | Yes | All iOS-side APIs in these docs are public (WebKit, UIKit, Metal, UIAccessibility). Runtime Objective-C subclassing in AccessKit's `SubclassingAdapter` uses the Objective-C runtime; prefer `Adapter` (U). |
| 2.5.2 | Apps should be self-contained; no downloading or executing code that changes features, narrow educational exception | Yes | Yes | Web pages run as web content in WKWebView: expected for a browser (U). Krypa must never download native or Rust code, and remote "app definitions" must be data (manifest fields), not code. |
| 2.5.4 | Multitasking apps may use background services only for intended purposes (VoIP, audio, location, task completion, local notifications) | Yes (media) | Yes | Background audio/PiP for web video needs the `audio` background mode (U). No other background use. |
| 2.5.6 | "Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript." | Yes | Yes | WKWebView satisfies it. Alternative engines exist only in the EU and (iOS 26.2+) Japan with engine-steward requirements and are not applicable ([Apple Japan](https://developer.apple.com/support/alternative-browser-engines-jp), V-doc). WPE is Android-only. |
| 2.5.8 | Apps that create alternate desktop/home screen environments are rejected | Low | **High** | A launcher of "installed web apps" is the main exposure. Mitigation: present installed apps as favourites/pinned sites inside a browser, never as a replacement for SpringBoard, no widget-like icon grid that mimics the home screen (U). |
| 2.5.19 | New (2026-10-16): clarifies policy on hidden, dormant, or undocumented features | Yes | Yes | No hidden developer menu or dormant features in release builds; `isInspectable` off in release (U). The new guideline text itself was not read; only Apple's news summary (V-doc [Apple news](https://developer.apple.com/news/?id=guidelines)). |
| 4.2 | App "should include features, content, and UI that elevate it beyond a repackaged website" | Yes | Yes | Browser chrome, tab switcher, profiles, etc. satisfy this for a browser. A thin wrapper per site would not. |
| 4.7 | Mini apps, games, plug-ins and similar "software that is not embedded in the binary" are allowed under conditions | Unclear | **Yes** | If Krypa curates or lists web apps it offers, it risks being treated as hosting mini apps (U). User-navigated websites in a browser are not obviously "offered software" (U; the guideline does not define this). |
| 4.7.1 | Mini software must follow privacy rules, filter objectionable material, offer reporting, follow 3.1 for digital goods | If 4.7 applies | Yes | |
| 4.7.2 | App "may not extend or expose native platform APIs ... without prior permission from Apple" | Yes | Yes | Design rule: no JS-to-native bridge exposed to page content. Krypa's own manifest probe runs app-authored constant script and returns data to native, nothing is exposed to the page (IOS_INTEGRATION.md 5.4, U). |
| 4.7.3 | No sharing of data or permissions with individual software "without explicit user consent in each instance" | If 4.7 applies | Yes | Krypa's per-origin permission decisions are consent per origin; check wording against 4.7.3 if a catalog exists (U). |
| 4.7.4 | Provide an index of the software with universal links to all of it | If 4.7 applies | **Yes** | Only if a catalog/launcher index is shipped. Browsers do not provide one (U). |
| 4.7.5 | Identify software exceeding the app's age rating; age-restriction mechanism | If 4.7 applies | Yes | |
| 5.1.1 | Apps that collect user or usage data need consent, privacy policy | Yes | Yes | Browsing history is sensitive; plan keeps it local (SQLite). No telemetry without consent (U design stance). |
| 5.1.2 | Tracking requires App Tracking Transparency permission | Yes | Yes | Krypa should track nothing (U). |

Default-browser entitlement requirements are in IOS_INTEGRATION.md 5.6 (V-doc [Apple](https://developer.apple.com/tutorials/data/documentation/xcode/preparing-your-app-to-be-the-default-browser.json)); the key point for the compliance posture is that Apple's own browser criteria (URL field, search, or curated bookmarks on launch; direct navigation to http(s) URLs) match "browser, not catalog".

Answer to "browser vs app catalog": Krypa as a **browser** is subject to 2.5.6, 2.5.1, 2.5.2, 2.5.4, 4.2, 5.1.x, and (if it holds the entitlement) the default-browser restrictions. Krypa as an **app catalog** would additionally trigger 4.7 to 4.7.5 and put 2.5.8 at high risk. The design should avoid curated catalogs, remote-defined app lists, and any home-screen-like experience in v1 (U product decision for the lead).
